# ТЗ: подбор кодов ОКПД2 профиля по полному справочнику (гибрид)

Владелец зоны — роль 3 (`backend/app/llm`). Делает коллега, ревью — роль 3.
Ветка: `scoring/okpd2-hybrid`. Оценка: 6–10 ч.

## Зачем

Из текста профиля («Мы поставляем кухонное оборудование для школ…») LLM сейчас выбирает
категории из ручного справочника `backend/app/llm/okpd2.py` (71 категория), а код
превращает их в правило `r_okpd` (оператор `prefix_in`, важность 3).

Проблема: если отрасли компании нет в справочнике, модель берёт «соседнюю» категорию
(кухонное оборудование → видеонаблюдение, командировки → гостиницы, поверка приборов →
измерительные приборы). Неверный код уводит подходящие закупки в «Пропустить». Это главная
причина ошибок на новых отраслях: holdout4 — 68%, слепой holdout5 — 79% (цель ≥ 80%).
Ручной справочник не масштабируется: под каждую новую отрасль нужна новая строка.

## Что сделать

Коды ОКПД2 профиля подбираются по **полному** классификатору в два шага:
поиск по смыслу даёт короткий список кандидатов, LLM выбирает из них подходящие.

```
текст профиля ──LLM (как сейчас)──► описание деятельности (правило subject/semantic_match)
                                        │
                     эмбеддинги e5 ─────┤ шаг 1: top-K ближайших позиций полного ОКПД2
                                        ▼
                     LLM (новый промпт) ─ шаг 2: выбрать подходящие коды из кандидатов (можно ни одного)
                                        ▼
                     правило r_okpd: prefix_in, выбранные коды, важность 3
```

### 1. Справочник ОКПД2

- Файл `data/okpd2.csv`: `code;name`. Уровни: класс (`XX`), подкласс (`XX.X`),
  группа (`XX.XX`), подгруппа (`XX.XX.X`), вид (`XX.XX.XX`). Глубже не нужно.
- Источник: у роли 2 есть классы и группы (ветка `parser/scoring-experiment`); полный
  классификатор ОК 034-2014 — открытые данные (Росстандарт / data.gov.ru). Объём —
  порядка 2–5 тыс. строк, без персональных данных.

### 2. Шаг 1 — кандидаты по смыслу (`backend/app/llm/okpd2_search.py`)

- Векторы названий считаются моделью проекта `intfloat/multilingual-e5-small` через
  `app/embeddings/service.py` (новых моделей и SDK не добавлять). Название — как
  `passage: `, описание деятельности — как `query: `.
- Векторы справочника считаются один раз и кэшируются: файл `.npy` рядом с CSV,
  собирается скриптом `backend/scripts/build_okpd2_index.py`, либо в памяти при первом
  обращении (`lru_cache`). Пересчитывать при каждом разборе профиля нельзя.
- Для каждого описания деятельности (значения правил `subject` / `semantic_match`; если их нет —
  `company_description`) взять top-K (K ≈ 15, параметр в `core/config.py`), объединить
  без повторов.
- Функция: `okpd2_candidates(activities: list[str], k: int) -> list[tuple[str, str]]`
  → список `(код, название)`.

### 3. Шаг 2 — выбор LLM

- Новый промпт `backend/app/llm/prompts/okpd2_pick.md`, первой строкой `version: 1`.
  Смысл: «вот деятельность компании и список кодов; выбери только те, что прямо называют
  то, чем она занимается; соседние не бери; если ничего не подходит — пустой список».
- Вызов только через `LLMClient.complete_json` (`app/llm/client.py`), temperature 0,
  JSON-схема: `{"codes": [...]}`, где `codes.items.enum` — коды кандидатов (модель
  не может придумать код не из списка).
- Ошибка или не-JSON → один повтор, затем правило по кодам не создаётся (профиль без
  ОКПД2 лучше, чем профиль с неверным кодом). Разбор профиля из-за этого не падает.
- **Примеры в промпте не брать из тестовых наборов** (`tests/dataset/scenarios_*.yaml`
  и holdout5) — иначе проверка станет нечестной.

### 4. Встраивание в разбор профиля

- В `backend/app/llm/parse_profile.py` функция `okpd2_rule(...)` получает коды из
  нового модуля вместо `codes_for(okpd2_categories)`. Правило то же: `id="r_okpd"`,
  `prefix_in`, важность 3, label «Коды ОКПД2: <названия выбранных позиций>».
- Коды, которые пользователь написал сам, объединяются с подобранными (как сейчас).
- **Без LLM или без модели эмбеддингов** — работает текущая схема (категории из
  `okpd2.py`). Ручной справочник не удалять: он — запасной путь.
- Поле `okpd2_categories` в ответе первого промпта можно оставить (для запасного пути)
  или убрать, подняв `version` промпта `parse_profile.md`.
- Движок скоринга (`backend/app/scoring/`) **не трогать**.

### 5. Уровень кодов

`prefix_in` совпадает по началу кода. Слишком общий код (`28` — «машины и оборудование»)
пропустит чужие закупки, слишком точный (`28.93.15.120`) — свои. Предлагать модели
кандидатов уровня группа / подгруппа / вид (`XX.XX`–`XX.XX.XX`); классы (`XX`) — только
если деятельность действительно широкая. Уровень проверяется калибровкой (раздел 7).

## Ограничения (из CLAUDE.md)

- LLM — только через `app/llm/client.py`; оценку LLM не ставит.
- Разбор профиля идёт в воркере Celery; лишний вызов LLM допустим (критерий «< 10 с»
  относится к оценке закупки, а не к разбору профиля).
- Типизация (mypy strict), ruff, тесты с моками LLM и эмбеддингов.
- Не коммитить `.env` и ключи.

## Как проверить

1. Юнит-тесты (`backend/tests/llm/`): кандидаты по фейковым векторам; выбор LLM по
   фейковому клиенту (`fake_llm` из `test_parse_profile.py`); код вне списка кандидатов
   отбрасывается; без LLM/модели работает запасной путь; сбой шага 2 не роняет разбор.
2. Калибровка на пяти известных наборах (из папки `backend`, наборы — в ветке
   `parser/draft-scenarios`):
   ```
   .venv\Scripts\python scripts\calibrate.py --scenarios scenarios_holdout4.yaml -q
   ```
   Наборы `scenarios_draft`, `_holdout`, `_holdout2`, `_holdout3`, `_holdout4`.
   Сравнить с текущей версией в `shishulick` (на момент ТЗ: 608 из 662 = 91,8%).
   Гибрид не должен ухудшать сумму; главное — рост на `holdout3` и `holdout4`
   (новые отрасли). Кэш правил `scripts/calibrate_rules.json` разбирается заново
   при смене версии промпта.
3. Финальная проверка — слепой прогон holdout5 у роли 3 (данные холдаута разработчику
   не передаются; подбирать что-либо под него нельзя). Ориентир — ≥ 80%.
