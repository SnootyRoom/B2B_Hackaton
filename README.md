# Скоринг закупок (AI Procurement Copilot, задача 4)

Веб-сервис для поставщика: загружаете извещения ЕИС (`.xml` / `.json`), система извлекает
параметры закупки, подтягивает данные заказчика из ЕГРЮЛ по ИНН и выдаёт оценку 0–100%,
рекомендацию «Участвовать / Рассмотреть / Пропустить» и обоснование.

## Запуск

```bash
cp .env.example .env      # ключи необязательны: без них система работает
docker-compose up --build
```

- Интерфейс: http://localhost:3000
- API и Swagger: http://localhost:8000/docs (контракт также в `docs/openapi.json`)
- Демо-вход: `demo@example.com` / `demo12345` (меняется в `.env`)

При старте бэкенд сам применяет миграции и создаёт демо-пользователя.

| Сервис | Что делает |
| --- | --- |
| `frontend` | nginx: статика React + прокси `/api` → `backend` (одно происхождение, cookie работают) |
| `backend` | FastAPI; синхронные ответы < 2 с, всё тяжёлое ставится в очередь |
| `worker` | Celery: парсинг → ЕГРЮЛ → эмбеддинг → оценка, по файлу за раз с прогрессом |
| `db` | PostgreSQL 16 + pgvector: данные и векторный поиск смыслового сравнения |
| `redis` | брокер очереди |

Модель эмбеддингов `intfloat/multilingual-e5-small` скачивается при сборке образа.

## Переменные окружения

См. `.env.example`. Комментарии в `.env` — только отдельной строкой: docker-compose считает
текст после `=` значением.

- `JWT_SECRET` — свой длинный случайный ключ для подписи входа.
- `LLM_API_KEY` и `LLM_FOLDER_ID` — доступ к YandexGPT. Пусто → правила задаются вручную,
  обоснование по шаблону.
- `DADATA_API_KEY` — ЕГРЮЛ. Пусто → только кэш и офлайн-профили `data/customers/<ИНН>.json`.

**Модель LLM:** YandexGPT Pro через Yandex AI Studio, `LLM_MODEL=yandexgpt/latest`
(URI `gpt://<каталог>/yandexgpt/latest`), temperature 0. Выбрана по тестовым сценариям:
сравнение трёх моделей на контрольной выборке дало одинаковую точность (91%), оставлена
YandexGPT Pro. Модель эмбеддингов e5-small тоже сравнивалась с альтернативами — замена
прироста не дала.

**Справочник ОКПД2:** `data/okpd2.csv` (`code;name`, ОК 034-2014 от класса до вида `XX.XX.XX`,
5654 кода, по дереву classifikators.ru) и индекс векторов `data/okpd2.npy` рядом. Коды профиля
подбираются по нему: кандидаты по смыслу (e5) → выбор LLM (`backend/app/llm/okpd2_search.py`,
промпт `okpd2_pick.md`). Индекс пересобирается после замены CSV:
`docker-compose run --rm -v ./data:/out -e OKPD2_CSV=/out/okpd2.csv backend python scripts/build_okpd2_index.py`.
Без справочника или модели коды берутся из ручных категорий `backend/app/llm/okpd2.py`.

## Как пользоваться

Интерфейс ведёт по шагам «профиль → загрузка → результаты» (стартовый экран показывает,
какой следующий):

1. **Вход.** Демо-аккаунт или регистрация (пустой аккаунт — пройти путь с нуля).
2. **Мой профиль.** Опишите своими словами, какие закупки интересны («Поставляем канцтовары
   в Томской области, аукционы до 2 млн») → «Составить правила». Правила появляются
   карточками: каждую можно поправить, выключить или удалить; фразы, которые система
   не поняла, показаны отдельно. Ниже — веса групп и пороги «Участвовать от» /
   «Рассмотреть от». «Сохранить и пересчитать» обновляет оценки уже загруженных закупок.
3. **Загрузка.** Перетащите файлы `.xml` / `.json` из ЕИС (образцы — `data/samples/`).
   Видно, какой файл разбирается, какой готов и почему какой-то не подошёл.
4. **Результаты.** Таблица: закупка, заказчик, НМЦК, регион, срок подачи, оценка
   и рекомендация (цвет всегда продублирован словом). Сортировка по оценке, цене, сроку;
   фильтр по периоду; выгрузка выборки в CSV или JSON.
5. **Карточка закупки.** Итог и короткое обоснование, «Как сложилась оценка» — вклад каждого
   правила или «нет данных», параметры закупки, позиции и данные заказчика из ЕГРЮЛ.

Раздел «История» — все загрузки с итогом по файлам. Вёрстка работает от ширины 375 px.
Для разработки фронта без бэкенда: `cd frontend && npm run dev` (демо-данные,
`VITE_USE_MOCK=true`); в Docker фронт собирается с настоящим API.

## Данные: ЕИС и ЕГРЮЛ

**Парсинг извещений** (`backend/app/parsers/`, вход — `parse_file`):

- `.xml` из ЕИС: адаптеры известных форматов — 44-ФЗ (формат 2020+ `epNotification*`
  и прежний `fcsNotification*`) и 223-ФЗ (`purchaseNotice*`); всё остальное (ПП РФ 615,
  архив 94-ФЗ, новые схемы) — универсальный адаптер по словарю синонимов тегов.
  Закон — информационное поле, логика от него не зависит.
- `.json` — по схеме `ProcurementData` (пример ниже).
- Извлекается: реестровый номер, предмет, НМЦК и валюта, способ закупки, закон, заказчик
  (ИНН, название), регион и место поставки, дата публикации, окончание подачи заявок,
  срок поставки, коды ОКПД2, позиции (название, количество, цена), обеспечение заявки
  и контракта, ограничения. Пути тегов по типам документов — `docs/eis-fields.md`.
- Многолотовое извещение → запись на каждый лот (`<номер>-<лот>`). Повторная загрузка
  того же номера обновляет запись.
- Ошибки по файлу, пакет не останавливается: «Файл не похож на выгрузку из ЕИС»
  (`UNSUPPORTED_FORMAT`), «Это не извещение о закупке» — протокол, контракт, план
  (`NOT_A_NOTICE`), «В файле не найдено: …» — нет номера, предмета или НМЦК
  (`MISSING_REQUIRED_FIELD`). Остальные поля могут отсутствовать — правила по ним
  получают «нет данных».

**Данные заказчика по ИНН** (`backend/app/egrul/`, в воркере): кэш в PostgreSQL
(`EGRUL_CACHE_TTL_DAYS`, по умолчанию 7 дней) → DaData → устаревший кэш, если DaData
недоступна → офлайн-профиль `data/customers/<ИНН>.json`. Берутся название, ОГРН, тип,
статус (действующая / реорганизация / ликвидация / ликвидирована / банкрот), дата регистрации
(возраст), основной ОКВЭД, адрес и регион, отметки о недостоверности. Источник виден
в карточке. Заказчик не найден или сервис недоступен — оценка всё равно считается,
правила о заказчике получают «нет данных». Офлайн-профиль — сохранённый ответ DaData
или JSON по схеме `CustomerData` (`backend/app/schemas/customer.py`).

## Скоринг и ИИ

**Оценку ставит детерминированный движок правил, не LLM** (`backend/app/scoring/`): одинаковые
закупка и профиль всегда дают одинаковый итог. LLM только переводит текст пользователя
в правила и подбирает коды ОКПД2; без ключа LLM правила задаются вручную.

**Профиль** — набор правил в трёх группах: «Закупка» (НМЦК, способ, регион, закон, сроки),
«Соответствие» (предмет по смыслу, коды ОКПД2), «Заказчик» (статус, возраст, отметки ЕГРЮЛ).
У правила есть поле, оператор, значение и важность 1–3. Правила по умолчанию: стоп
«приём заявок завершён», стоп «заказчик ликвидируется / банкрот», «заказчик действующий»,
«нет отметок о недостоверности», «заказчик работает не меньше 3 лет».

**Расчёт** (`engine.py`):
1. Стоп-фактор сработал → 0%, «Пропустить», причина первой строкой.
2. Каждое правило даёт частичный балл 0–1. Поля нет — правило пропускается с пометкой
   «нет данных»; пропущено больше половины веса группы — флаг «мало данных».
3. Балл группы — среднее по важности; итог — группы с весами 0,40 / 0,35 / 0,25 (вес группы
   без данных переходит остальным).
4. Рекомендация: ≥ 70 — «Участвовать», ≥ 40 — «Рассмотреть», ниже — «Пропустить».
5. Ограничители, чтобы хорошие второстепенные условия не вытягивали чужую закупку:
   предмет не похож на деятельность компании или сумма больше чем в 2 раза за диапазоном —
   не выше «Пропустить»; явное условие профиля не выполнено — не выше «Рассмотреть».

**Предмет по смыслу** — косинусная близость e5 текста закупки (предмет + позиции) и описания
деятельности: 0 баллов при 0,82, полный балл при 0,86. Коды ОКПД2 сравниваются по началу кода.

**Обоснование** собирается по шаблонам из результатов правил, каждая фраза со ссылкой
на правило: «Стоп-фактор: приём заявок завершён [stop_deadline]».

**Разбор текста профиля** (`backend/app/llm/parse_profile.py`, промпт `parse_profile.md`, версия 10):
LLM возвращает правила по JSON-схеме, каждое проверяется теми же валидаторами, что и при
сохранении. Код дополнительно сверяет суммы с числами в тексте, строит стоп-фактор
«только …», убирает правило о регионе у компаний «по всей России» и отбрасывает категории
ОКПД2, далёкие по смыслу от деятельности. Ошибка → один повтор; оборванный ответ —
повтор и сохранение целых правил; не вышло — «задайте правила вручную».

### Как поменять параметры без кода

- Профиль: текстом (разбор LLM) или в редакторе правил; `PUT /api/scoring-profiles/active`
  с `"rescore": true` пересчитывает загруженные закупки.
- Веса групп и пороги рекомендации — часть профиля.
- Калибровочные настройки — переменные в `.env` (затем перезапуск `backend` и `worker`):
  `SEMANTIC_C0`, `SEMANTIC_C1` (пороги смысла), `FIT_MIN`, `SEMANTIC_LIFT`,
  `OKPD2_MISS_WEIGHT`, `OKPD2_CATEGORY_MIN`, `MONEY_FAR_FACTOR`, `OKPD2_CANDIDATES_K`.
  Значения по умолчанию и смысл — в `backend/app/core/config.py`.

### Скорость и точность

- Оценка одной закупки — до 0,14 с; вместе с парсингом, ЕГРЮЛ и эмбеддингом — 3–4 с на файл.
- Точность рекомендации на размеченных сценариях роли 2 (`tests/dataset/scenarios_*.yaml`):

  | Набор | Сценариев | Точность |
  | --- | --- | --- |
  | draft, holdout 1–4 (использовались при настройке) | 662 | 92,6% |
  | holdout 5: 50 новых профилей, проверка вслепую* | 210 | 80% |

  \* Набор не видел ни разработчик, ни модель: его прогоняла участница команды и передала
  только итоговую цифру. Каждый новый набор прогоняется один раз, без подгонки под него.
  Цифра получена до подбора кодов по полному справочнику ОКПД2.

Как воспроизвести (правила профилей уже разобраны и лежат в `scripts/calibrate_rules.json`,
ключ LLM не нужен):

```bash
docker-compose exec backend python scripts/calibrate.py --scenarios scenarios_holdout4.yaml -q
```

Без `-q` выводится каждая закупка с баллом, ожиданием и правилами для ошибок.
Наборы: `scenarios_draft.yaml`, `scenarios_holdout.yaml`, `scenarios_holdout2.yaml` … `_holdout4.yaml`.

## Как устроена обработка

1. `POST /api/procurements/upload` сохраняет файлы и сразу отвечает `202 {"task_id"}` —
   поэтому большие пакеты не дают 504.
2. Воркер обрабатывает файлы по одному; ошибка в файле не останавливает пакет.
3. Фронт опрашивает `GET /api/tasks/{id}` раз в 1–2 с: `processed` из `total`, статусы файлов.
4. Итог задачи: `done` / `partial` / `failed`.

Ошибки API всегда в формате `{"error": {"code", "message", "details"}}`.
Чужие записи → 404. Суммы в JSON — числа (внутри `Decimal`), даты — ISO 8601 в UTC.

## Примеры запросов

```bash
# вход (cookie сохраняется в jar)
curl -c jar -H 'Content-Type: application/json' \
  -d '{"email":"demo@example.com","password":"demo12345"}' localhost:8000/api/auth/login
curl -b jar localhost:8000/api/auth/me
curl -c jar -H 'Content-Type: application/json' \
  -d '{"email":"me@example.com","password":"password123"}' localhost:8000/api/auth/register
curl -b jar -X POST localhost:8000/api/auth/logout

# загрузка и прогресс
curl -b jar -F files=@tests/dataset/procurements/0102200001626002273.xml -F files=@notice.json \
  localhost:8000/api/procurements/upload            # → {"task_id": "..."}
curl -b jar localhost:8000/api/tasks/<task_id>
curl -b jar "localhost:8000/api/tasks?kind=upload"  # история загрузок

# закупки и результаты
curl -b jar localhost:8000/api/procurements
curl -b jar localhost:8000/api/procurements/<id>    # карточка: данные, заказчик, оценка
curl -b jar localhost:8000/api/results              # таблица, по убыванию оценки

# профиль скоринга
curl -b jar localhost:8000/api/scoring-profiles/catalog   # поля для правил, регионы, llm_enabled
curl -b jar localhost:8000/api/scoring-profiles/active
curl -b jar -X PUT -H 'Content-Type: application/json' \
  -d @profile.json localhost:8000/api/scoring-profiles/active   # "rescore": true → task_id
curl -b jar -H 'Content-Type: application/json' \
  -d '{"text":"Интересны аукционы в Томской области до 10 млн"}' \
  localhost:8000/api/scoring-profiles/parse         # → task_id, правила в TaskOut.result

# пересчёт и заказчик
curl -b jar -H 'Content-Type: application/json' -d '{}' localhost:8000/api/score
curl -b jar localhost:8000/api/organizations/7017000019   # 200 из кэша, иначе 202 + task_id
```

Формат JSON-файла закупки — схема `ProcurementData` (объект или список лотов):

```json
{"reg_number": "0365000000000000001", "subject": "Сопровождение ПО",
 "nmck": 4200000, "method": "auction", "customer_inn": "7017000019",
 "region": "Томская область", "application_deadline": "2026-11-20T10:00:00Z"}
```

## Разработка

```bash
docker-compose exec backend pytest
docker-compose exec backend sh -c "ruff check . && ruff format --check . && mypy app"
docker-compose exec backend python /repo/tests/dataset/evaluate.py   # проверка тестовых данных
docker-compose exec backend python scripts/calibrate.py --scenarios scenarios_holdout4.yaml -q  # точность
docker-compose exec backend alembic revision --autogenerate -m "..."  # после изменения моделей
```

Правила команды, роли и архитектура — в `CLAUDE.md`; ТЗ и аналитика — в `docs/`.

### Контракты между модулями

| Модуль (роль) | Функция, которую вызывает конвейер |
| --- | --- |
| `parsers/registry.py` (2) | `parse_file(content, filename) -> list[ProcurementData]`, ошибки — `ParseError` |
| `egrul/service.py` (2) | `lookup(db, inn) -> CustomerLookup` (воркер), `get_cached(db, inn)` (API, без сети) |
| `scoring/engine.py` (3) | `score(profile, fields, similarity) -> ScoreResultData`, поля — `extract_fields(procurement, customer, now)` |
| `embeddings/service.py` (3) | `embed_passage(text)`, `similarity_in_db(db, procurement_id, query)` (pgvector) |
| `llm/client.py` (3) | `parse_profile_text(db, text) -> ParseProfileResult`, ошибки — `LLMError` |

Схемы — `backend/app/schemas/`. Меняете схему → обновите `docs/openapi.json`, фронт и тесты в том же PR.
