## Что строим

Веб-сервис для **поставщика**: он загружает извещения ЕИС (`.xml` / `.json` / `.zip`),
система извлекает параметры закупки, по ИНН заказчика подтягивает данные ЕГРЮЛ и выдаёт
оценку 0–100%, рекомендацию «Участвовать / Рассмотреть / Пропустить» и обоснование
со ссылками на параметры. Пользователи входят по логину; данные каждого изолированы.

Критерии приёмки ТЗ:
1. Парсинг ЕИС — корректно извлекаются ключевые параметры (НМЦК, тип процедуры, регион, сроки).
2. ЕГРЮЛ — данные организации по ИНН.
3. Параметры скоринга меняются без изменения кода.
4. Оценка одной закупки < 10 с.
5. Обоснование ссылается на параметры.
6. ≥ 80% совпадений с тестовыми сценариями.
7. Запуск `docker-compose up --build`.
Плюс: README, нет 504 на больших пакетах, интерфейс понятен без технических знаний.

## Главные архитектурные правила (не нарушать)

1. **Оценку считает детерминированный движок правил, не LLM.** LLM используется только для:
   (а) текст параметров → черновик JSON-правил, (б) текст обоснования,
   (в) [P2] последний шаг парсинга, если адаптеры не нашли обязательные поля.
   Одинаковый вход всегда даёт одинаковую оценку.
2. **Всё тяжёлое — через Celery.** Синхронный эндпоинт отвечает < 2 с: принимает данные и
   возвращает `task_id`. Парсинг, ЕГРЮЛ, скоринг и LLM выполняются в воркере.
3. **Система работает без внешних сервисов.** Нет LLM-ключа → правила задаются вручную,
   обоснование собирается по шаблону. DaData недоступна → кэш → офлайн-профили
   `data/customers/<inn>.json`. Ошибка внешнего сервиса никогда не роняет обработку.
4. **Парсер не привязан к закону.** Поддерживаются любые извещения ЕИС (44-ФЗ, 223-ФЗ,
   ПП РФ 615, архив 94-ФЗ). Цепочка: адаптер известного формата (44-ФЗ, 223-ФЗ) →
   универсальный адаптер (поиск по словарю синонимов тегов) → [P2] LLM.
   Закон — информационное поле.
5. **Ошибка в одном файле не срывает пакет.** У каждого файла свой статус `ok` / `error`
   с кодом ошибки.
6. **Изоляция по пользователю.** Все запросы к `ScoringProfile`, `Procurement`, `ScoreResult`,
   `Task` фильтруются по `owner_id`. Чужая запись → 404. `CustomerProfile` общий.
7. **Контракты — источник правды.** Pydantic-схемы в `backend/app/schemas/` и OpenAPI.
   Меняете схему → обновляете фронтовый клиент и тесты в том же PR.

### LLM

- Кандидаты: **GPT-6 Luna** и **Claude Haiku 5.5** через ProxyAPI. Итоговая выбирается по
  прогону `tests/evaluate.py` на обеих; выбранный точный идентификатор модели фиксируется
  в README (обязательно).
- Весь доступ к LLM — только через `backend/app/llm/client.py`. Нигде больше не импортировать
  SDK провайдеров.
- Разбор параметров: temperature 0, структурированный вывод по JSON-схеме, валидация Pydantic,
  один повтор с текстом ошибки, затем понятная ошибка пользователю.
- Кэш ответов по хэшу (вход + модель + версия промпта) в Postgres.
- Обоснование от LLM проверяется: каждое число в тексте должно быть во входных данных,
  иначе используется шаблон.
- Промпты лежат в `backend/app/llm/prompts/*.md`, у каждого есть версия.

## Доменная модель (кратко)

- **Procurement** — один лот извещения. Обязательные: `reg_number`, `subject`, `nmck`,
  `parsed_by`. Остальное может отсутствовать (`None` = «нет данных»). Многолотовое
  извещение → запись на каждый лот, номер `<reg_number>-<номер лота>`. Позиции внутри лота
  не делятся, хранятся в `items`. Повторная загрузка того же номера тем же пользователем
  обновляет запись.
- **CustomerProfile** — данные ЕГРЮЛ по ИНН; поле `source`: `dadata` / `cache` /
  `stale_cache` / `offline`. Статусы: `active`, `reorganizing`, `liquidating`, `liquidated`,
  `bankrupt`, `unknown`.
- **ScoringProfile** — веса групп (по умолчанию 0,40 / 0,35 / 0,25), пороги (70 / 40), правила.
- **ScoringRule** — `group` (`procurement` / `fit` / `customer`), `kind` (`stop` / `weighted`),
  `field` из каталога, `operator`, `value`, `weight` (1 / 2 / 3 = низкая / средняя / высокая),
  `soft_margin`, `label`.
- **ScoreResult** — итог, баллы групп, флаги «мало данных», стоп-факторы, по каждому правилу:
  значение поля, частичный балл, вклад в итог, текст обоснования.
- **User** — email, хэш пароля. Одна роль, без админки.

## Скоринг (формулы — в аналитике, раздел «Движок»)

- Порядок: стоп-факторы → частичные баллы правил (0–1) → баллы групп (0–100) → итог.
- Стоп-фактор сработал → итог 0, «Пропустить», причина первой строкой.
- Поля нет → правило пропускается (не в числителе и не в знаменателе), пометка «нет данных».
  Пропущено > 50% веса группы → флаг «мало данных». Группа без применимых правил исключается,
  её вес переходит остальным пропорционально.
- `semantic_match`: косинусная близость e5, линейно от 0 при 0,55 до 1 при 0,80
  (пороги калибруются, лежат в настройках, не в коде).
- Правила по умолчанию (`scoring/defaults.py`): стоп «приём заявок завершён», стоп
  «заказчик ликвидируется / ликвидирован / банкрот», «заказчик действующий» (3),
  «нет отметок о недостоверности» (3), «возраст заказчика ≥ 3 лет» с допуском (2).
- Рекомендация зависит только от итога и стоп-факторов. Обоснование её не меняет.
- Шаблонное обоснование отдаётся сразу, LLM-текст подменяет его в фоне.

## API

Все под `/api`, все кроме `auth/register` и `auth/login` требуют входа.

```
POST /auth/register   POST /auth/login   POST /auth/logout   GET /auth/me
POST /procurements/upload          # файлы (P0), zip-архив [P1] → task_id
POST /procurements/fetch           # [P2] реестровые номера → task_id
GET  /procurements   GET /procurements/{id}
GET  /organizations/{inn}
POST /scoring-profiles/parse       # текст → черновик правил (LLM)
GET/PUT /scoring-profiles/active   # P0: один профиль на пользователя
GET/POST /scoring-profiles         # [P1] несколько профилей, POST /scoring-profiles/{id}/activate
POST /score                        # пересчёт по профилю → task_id
GET  /results                      # P0
GET  /results/export?format=csv|json  # [P1]
GET  /tasks/{id}                   # статус: queued / processing / done / partial / failed
```

Ошибки в едином формате: `{"error": {"code": "MISSING_REQUIRED_FIELD", "message": "<текст для пользователя>", "details": {...}}}`.
Коды и тексты — в аналитике (раздел «Загрузка и фоновая обработка»).

## Соглашения по коду

- Типизация везде (mypy без ошибок, TS strict). Без `Any`, если можно обойтись.
- Деньги — `Decimal`, никогда `float`. Даты — UTC в БД, местное время только в интерфейсе.
- Не логировать ключи, пароли, токены.
- Внешние вызовы (DaData, LLM, ЕИС) — только через свои сервисные модули, с таймаутом
  и обработкой ошибок; в тестах они мокаются.
- Новый тип документа ЕИС = новый адаптер + образец в `data/samples/` + юнит-тест с эталоном
  + строка в `docs/eis-fields.md`.
- Новый критерий скоринга = поле в каталоге + оператор (если нужен) + шаблонная фраза
  обоснования + тест. Остальной код не трогается.
- Все тексты интерфейса на русском, без технических терминов. Суммы: `4 200 000 ₽`,
  в таблице `4,2 млн ₽`. Даты `ДД.ММ.ГГГГ`. Цвет рекомендации всегда дублируется словом.
- Вёрстка работает от ширины 375 px.

## Git

- PR в `main` с ревью от одного человека; `main` всегда запускается через

## Роли и зоны ответственности

Каждая роль владеет своей частью целиком: пишет её, проверяет и отвечает за результат.

| Роль | За что отвечает | Критерии ТЗ | Каталоги |
| --- | --- | --- | --- |
| 1 — тимлид, бэкенд-ядро, инфраструктура | Контракты (схемы, OpenAPI) — первыми; запуск одной командой; авторизация и изоляция данных; фоновая обработка пакета (файл → парсинг → ЕГРЮЛ → оценка); склейка модулей, ревью, README | 7, отсутствие 504, README | `backend/app/core`, `api`, `tasks`, `models`, `schemas`, миграции, `docker-compose.yml`, README |
| 2 — данные ЕИС и ЕГРЮЛ | Сбор образцов XML; парсер любых извещений → `Procurement`; данные заказчика по ИНН через DaData с кэшем и офлайн-профилями | 1, 2 | `backend/app/parsers`, `egrul`, `data/samples`, `data/customers`, `docs/eis-fields.md` |
| 3 — скоринг и ИИ | Движок оценки 0–100% и рекомендации; LLM: текст параметров → правила и обоснование; эмбеддинги для смыслового сравнения; выбор модели; калибровка весов | 3, 4, 5, 6 | `backend/app/scoring`, `llm`, `embeddings` |
| 4 — фронтенд | Все экраны: вход, параметры с редактором правил, загрузка с прогрессом, результаты, карточка закупки; понятность без инструкции | интерфейс для не-технических пользователей | `frontend/` |
| 5 — тестовые данные и качество | Тестовый набор с заранее размеченными ожидаемыми оценками; `evaluate.py` (точность, скорость, полнота парсинга); прогоны и баги владельцам; демо-набор | измеряет 1, 4, 6 | `tests/dataset`, `tests/evaluate.py`, `data/demo` |

Зависимости: роль 1 даёт всем контракты и каркас → роль 2 даёт данные роли 3 → роль 3
даёт оценки роли 4 → роль 5 проверяет результат всех и возвращает ошибки владельцам.
Пока контракты не в `main`, остальные работают против моков по аналитике.

Правите чужую зону — предупредите владельца в PR.

## Чего не делать

- Не просить LLM поставить оценку или рекомендацию.
- Не делать синхронных вызовов LLM / DaData / ЕИС в обработчиках API.
- Не хардкодить веса, пороги и правила в коде — только данные профиля и `defaults.py`.
- Не завязывать логику на номер закона или конкретный путь тега вне адаптеров.
- Не коммитить `.env`, ключи, выгрузки с персональными данными.
- Не отдавать чужие данные: каждый запрос — с фильтром по `owner_id`.
